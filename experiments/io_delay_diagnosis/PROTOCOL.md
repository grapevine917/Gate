# 质量下降查询与延迟展开诊断

复用 io_predictability 的 state_lr 分类器、验证集冻结的三档阈值（非目标类别 FPR 预算 0.1%、0.5%、1%）和原有 SIFT1M / DEEP1M 各 1,000 条测试查询。模型没有重训、阈值没有用测试反馈调整。固定 L=100、k=10、beam=4、BFS cache=10,000，展开/请求数不设硬上限，ET 和 reorder 关闭。以下属于测试集上的事后诊断与机制敏感性实验，不作为新策略在独立测试集上的泛化证明。

## 定位有效的保护干预

记录原生动态剪枝每次被跳过候选的读取前 retain 分数、已完成展开数、候选队列排名、相对 PQ 距离等。对于 Recall@10 低于原始搜索的查询，逐个保护其实际被剪节点，运行完整搜索；模型函数、阈值、入口、缓存和队列容量均固定，其他决策仍按改变后的当前状态重新评分。保护后 Recall 增加的节点称为“有效保护节点”，不是声称它是唯一、必要原因。

阶段用已完成展开数明确划分：0–9、10–39、40–79、≥80。这是操作性的进度分桶，不把 retset 排名当作展开次数，也不从非连续展开序列构造虚假的连续图路径。排名只表示候选当前在 L 容量队列中的位置。

统计单节点充分恢复的查询数、有效节点的原始结果/GT 角色、跨失败查询的节点复用率，并连接先前 baseline 单节点标签。先前单节点安全标签不保证联合路径中的安全性。不同阈值重复出现的同一 (query,node) 需要去重；主阶段表分别按阈值报告，主集中度表按查询—节点对去重。

额外将每条失败查询的全部有效保护节点组成联合保护名单，再执行真实联合重放。该保护名单由测试反馈定义，属于 Oracle 诊断；不能宣称可部署，也没有证明名单大小最小。名单大小与实际新增请求数分别报告。

## 延迟机制

默认 online_defer_limit=0 完全沿用永久剪枝。实验模式将被模型拒绝的候选存入独立内存表，仍消耗原有 beam 槽位，不立即读取或 exact scoring。第一阶段候选队列耗尽后进入恢复阶段：直接展开延迟候选，避免将其重新插入原队列时因为重复 ID、容量和距离边界而被丢弃。

恢复阶段关闭分类剪枝。每个恢复节点的邻居使用原始 best-first 队列继续搜索，优先完成当前活跃候选，再选择下一个延迟节点；沿用 visited 集合、L 容量队列、精确结果集合和原图，不重置搜索。三种延迟节点选择规则：PQ 距离从小到大；拒绝时 retain 分数从高到低（较接近拒绝阈值）；拒绝时队列排名从小到大。相等时按 PQ 距离与 ID 排序。

预算为 1、4、8、16、32 或全部延迟种子节点。**种子预算不是所有后代展开数或请求数的硬预算**；恢复节点的邻接展开及随后活跃候选搜索均计入成本。全程没有读取完整邻接表来获得免费的调度特征，也没有使用测试 GT 选择延迟节点。延迟表占用额外 O(被拒绝候选数) 内存，当前实现线性扫描选取候选，未做生产性能优化。

对全部 1,000 条查询启用延迟策略，而不是只对已经知道会失败的查询补搜。逐次原生重放断言：延迟第一阶段的评分/决策状态序列与永久剪枝完全相同；补展开数不超过种子预算和延迟节点数。报告原失败恢复数、剩余下降查询、新增下降查询、严格结果一致数、平均展开数以及净请求节省。

I/O 单位为 **Submitted SSD Read Requests**，即 O_DIRECT Reader 提交的读取请求，不是 Physical SSD I/O。恢复阶段请求和新发现节点请求全部计入；不将各单节点保护收益相加。该轮耗时有记录但未做重复性能测量，不据此给出稳定延迟加速结论。
